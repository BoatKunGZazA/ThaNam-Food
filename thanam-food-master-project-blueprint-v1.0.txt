- Inventory
- Printer
- Notification
- Reports
- Audit

Core Channels:
ONLINE, POS, TABLE, BACK_OFFICE

Fulfillment:
DELIVERY, PICKUP, DINE_IN

หลักการสำคัญ:
- Online + POS + Table ใช้ Core เดียวกัน

17. DATABASE PRINCIPLES
============================================================
- PostgreSQL เป็น Source of Truth
- UUID Primary Key
- Money = NUMERIC(12,2)
- ห้ามใช้ Float/Double กับเงิน
- Time = TIMESTAMPTZ
- Flexible fields ใช้ JSONB เท่าที่จำเป็น
- PostGIS สำหรับ Geometry
- Foreign Key ทุกความสัมพันธ์สำคัญ
- Core business fields เป็น NOT NULL
- Historical records ไม่ควรลบ
- OTP / Session token ต้อง Hash
- Important mutations ต้องมี Idempotency
- Important operations ใช้ Transaction
- Row Lock เมื่อจำเป็น
- Prisma Migrations อยู่ใน Repository
- Production ใช้ prisma migrate deploy
- ห้ามใช้ db push ใน Production

PART 13 — DEVELOPMENT GOVERNANCE — LOCKED
============================================================

13.1 Coding Governance
----------------------
The implementation must follow this pipeline for every protected API operation:

Request
→ Schema Validation
→ Authentication
→ Authorization / RBAC
→ Object Ownership
→ Business Validation
→ Transaction
→ Database Constraint
→ Audit
→ Outbox Event
→ Realtime / Notification / Background Job

Rules:
- Controllers handle transport concerns only.
- Business rules belong in Services / Domain logic.
- Frontend is never the Business Authority.
- Database constraints remain the final integrity boundary.
- Critical mutations must be transactional where applicable.
- Important mutation APIs must support idempotency.
- Do not bypass Service / State Machine logic by directly updating critical status fields.
- Avoid giant files and hidden side effects.
- Every module must have clear responsibility and dependency direction.

13.2 Standard Error Handling
----------------------------
Every API must use a consistent response structure.

Success:
{
  "success": true,
  "data": {}
}

Error:
{
  "success": false,
  "error": {
    "code": "PRICE_CHANGED",
    "message": "ราคาสินค้ามีการเปลี่ยนแปลง กรุณาตรวจสอบรายการอีกครั้ง",
    "request_id": "req_123456"
  }
}

Rules:
- error.code is always a stable string.
- Frontend must branch on error.code, not on message text.
- message is user-facing Thai text.
- ErrorCode must come from the centralized Error Catalog.
- Do not expose SQL, stack traces, server paths, secrets, tokens, internal configuration, or sensitive infrastructure details.
- Production responses must use safe messages.
- Important requests should carry a request_id for tracing.
- HTTP status and ErrorCode are separate concepts.

13.3 Schema Validation — Zod
----------------------------
Zod is the standard schema-validation library.

Use Zod for:
- Request body validation
- Query parameter validation
- Path parameter validation
- API input validation
- Form validation where appropriate
- Environment variable validation
- Important external API response validation

Rules:
- Shared schemas should be reusable between frontend and backend where appropriate.
- Zod validates structure/type/format.
- Zod does NOT replace business rules.
- Business rules remain in Backend Services.
- Database constraints remain the final integrity layer.
- Validation errors must map to VALIDATION_ERROR or a more specific ErrorCode when defined.

13.4 Environment Policy
-----------------------
Three environments are required conceptually:

LOCAL
STAGING
PRODUCTION

Rules:
- No hardcoded secrets.
- No API keys/passwords/tokens committed to Git.
- `.env.example` contains names/placeholders only.
- Local, Staging, and Production must use separate database/configuration resources.
- Production must never be used accidentally by Local development.
- Redis, Storage, external API credentials, SMS credentials, payment credentials, and database credentials must be environment-specific.
- Production must disable debug output.
- Production must not expose stack traces.
- Secrets must be injected through environment variables or an appropriate secret-management mechanism.
- Environment variables should be validated at application startup.
- Missing required production configuration must fail startup safely rather than silently using defaults.

Recommended files:
.env.example
.env.local
.env.staging
.env.production

Actual production secrets must NOT be stored in the repository.

13.5 Configuration Governance
-----------------------------
Business configuration that should change during operations must be manageable through Back Office Settings where appropriate.

Do not hardcode:
- Store hours
- Order cutoff
- Delivery fees
- Delivery zone configuration
- Menu availability
- Promotion rules
- Operational switches
- Notification preferences
- Printer routing
- Other business-controlled values

Technical configuration may remain in environment/config files.

13.6 Logging vs Audit
---------------------
Application Log:
- Technical/runtime diagnostics
- Errors
- Performance
- Infrastructure events

Audit Log:
- Business and security actions
- Who changed what
- Before/after where appropriate
- Reason
- Timestamp
- Related record
- Actor / role

They are separate systems.

PART 14 — STATE TRANSITION MATRIX — LOCKED
============================================================

14.1 Core Principle
-------------------
Order status may ONLY change through an approved State Transition.

Any transition not explicitly allowed by this matrix is DENIED.

Frontend must never directly set a protected Order status.
Controller must not directly assign Order.status.
All transitions must pass through StateMachineService / OrderService.

14.2 Allowed Order Transitions
------------------------------

| From                  | To                    | Allowed Role |
|-----------------------|-----------------------|--------------|
| PENDING_CONFIRMATION  | ACCEPTED              | OWNER / MANAGER / KITCHEN |
| PENDING_CONFIRMATION  | REJECTED              | OWNER / MANAGER / KITCHEN |
| PENDING_CONFIRMATION  | CANCELLED             | Customer / authorized staff according to policy |
| ACCEPTED              | PREPARING             | OWNER / MANAGER / KITCHEN |
| PREPARING             | READY                 | OWNER / MANAGER / KITCHEN |
| READY                 | DELIVERY              | OWNER / MANAGER / DELIVERY |
| READY                 | SERVED                | OWNER / MANAGER / KITCHEN |
| DELIVERY              | ARRIVED               | DELIVERY |
| ARRIVED               | DELIVERED             | DELIVERY |
| DELIVERED             | COMPLETED             | SYSTEM / AUTHORIZED STAFF |
| SERVED                | COMPLETED             | OWNER / MANAGER / KITCHEN |

14.3 Explicitly Forbidden Transitions
-------------------------------------
Unless a separate correction workflow is explicitly defined:

ACCEPTED → PENDING_CONFIRMATION       DENIED
PREPARING → ACCEPTED                  DENIED
READY → PREPARING                    DENIED
DELIVERY → PREPARING                 DENIED
DELIVERED → PREPARING                DENIED
COMPLETED → PREPARING                DENIED
COMPLETED → DELIVERED                DENIED
COMPLETED → VOID                     DENIED
PENDING_CONFIRMATION → COMPLETED     DENIED

Every forbidden transition must return INVALID_ORDER_TRANSITION.

14.4 Final State
----------------
COMPLETED is a final business state.

Historical completed Orders must not be edited directly.

Corrections must use an explicit Adjustment / Refund / Correction workflow with Audit.

14.5 Cancellation
-----------------
Customer cancellation:
- Allowed before PREPARING, subject to policy.
- After PREPARING, requires staff decision/contact workflow.

Staff cancellation:
- Must be authorized.
- Must record reason.
- Must create timeline + audit.

14.6 Rejection
--------------
Order rejection must use a reason code:

OUT_OF_STOCK
OUTSIDE_DELIVERY_ZONE
STORE_ISSUE
CUSTOMER_UNREACHABLE
PAYMENT_ISSUE
OTHER

14.7 Payment State Is Independent
---------------------------------
Payment status must not be used as a substitute for Order status.

Order and Payment each have their own State Machine.

14.8 Kitchen State
------------------
Kitchen Job:
PENDING → IN_PROGRESS → READY → COMPLETED

Kitchen must not arbitrarily modify Order state.
Kitchen actions go through KitchenService / OrderService.

14.9 Delivery State
-------------------
UNASSIGNED → ASSIGNED → PICKED_UP → EN_ROUTE → ARRIVED → DELIVERED

Abnormal:
FAILED / CANCELLED

ASSIGNED does not mean PICKED_UP.

14.10 Printer State
-------------------
PENDING → PRINTING → PRINTED

Failure:
FAILED

Printer failure does not change Order state.

15.7 Transaction Boundary Rule
------------------------------
Do NOT put every external subsystem into one database transaction.

The architecture deliberately separates Core Business Transaction from asynchronous subsystems.

Core transaction includes business records that must be atomically created together.

After COMMIT:
Outbox / Worker handles:
- Printer
- Notification
- Realtime
- Inventory reconciliation/deduction where designed asynchronously
- Other external or retryable side effects

Therefore:

Printer failure:
→ Order remains valid
→ Print Job = FAILED
→ Retry / Reprint

Notification failure:
→ Order remains valid
→ Notification retries

Realtime failure:
→ Order remains valid
→ Client reconnects and syncs from API

Inventory deduction failure:
→ Confirmed Order remains valid
→ Reconciliation / Retry Job
→ Do not silently delete or corrupt Order

This rule supersedes any design that would rollback a confirmed Order merely because a printer, notification, realtime transport, or asynchronous inventory worker failed.

15.18 Rollback Strategy
-----------------------
Application rollback:
- Keep deployable previous image/version.
- If new application version fails health/smoke tests, revert application version.

Database rollback:
- Do not assume arbitrary destructive migration rollback is safe.
- Prefer backward-compatible migrations.
- Backup before high-risk production migration.
- Use forward-fix when necessary.
- Never destroy historical business data to perform a rollback.
